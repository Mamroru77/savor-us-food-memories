# 地标快印：按用户参考图应用

基线：`bcd181a`。本批仅改变客户端地图标记及临时图片合成，未修改云函数。

## 视觉实现

以用户自制图为准，重绘为透明底高分辨率 PNG：照片框、左上深绿 S 标、右下奶白叉勺标。

- **选中态：**80 × 89.375 逻辑像素，右上绿勾，zIndex 9999。
- **常态：**48 × 53.625 逻辑像素，不带绿勾，zIndex 100。
- 绿勾仅表示当前选中，不表示认证、收藏或云同步成功。
- 锚点固定为 `{x:0.5,y:276/286}`，对应底部主尖端，不把阴影或照片中心当作地点坐标。
- 保留点击标记居中、显式全览的逻辑，并补上餐厅名称 callout 点击事件。
- 深浅主题共用有奶白轮廓的标记，不修改主题体系、Map 卡片尺寸或 Me 高度。

设计预览：`docs/design/landmark-stamp-preview.png`，使用示例照片，非真机截图。
用户参考图：`docs/design/landmark-user-reference.png`。

## 真实照片，而非固定示例贴图

优先使用 `Memory.placePhoto`，其次使用非 `noPhoto` 记录的 `Memory.photo`。没有照片时使用同风格占位，绝不把默认示例餐食当作真实门店照片。

原生地图需要合成后的 iconPath：

1. Map 内使用位于屏幕外的原生 `canvas type="2d"`，不依赖 Web Canvas、React 或外部图形库。
2. `utils/mapMarkers.js` 按原图比例居中裁切，叠加对应选中／常态框架，生成临时 PNG。
3. `cloud://` 图片仅通过中央 `cloudRecords.downloadMapPhoto` 下载，不开放存储桶、不生成长期公开 URL，也不上传合成图片。
4. 页面和标记立即使用打包好的占位 PNG；照片合成成功后只更新 iconPath，不改变坐标、不重新移动相机。
5. 图片失败、原生 Canvas 不可用、导出失败等都回退到可点击的占位标记。

## 生命周期与性能边界

- 合成任务串行执行，优先所选记录；每次刷新最多增强 48 个地点，其余保留占位标记，所有地点仍在地图上。
- 缓存按图片来源和选中状态区分，一次地图显示周期最多缓存 96 个合成任务；达到上限使用占位，离开地图后重置。
- 快速切换、筛选、页面隐藏时，旧任务不会把过时图片填到新的 marker ID。
- 云图片临时下载副本在合成后清理；导出的派生 PNG 在离开地图时清理；迟到的导出也会清理。不会删除原始照片、草稿或 outbox 引用。
- 网络图片需要当前微信环境允许访问；不绕过平台权限或域名限制。不可访问时使用占位。

## 本地验证

**192/192 静态检查、119/119 mock 场景通过**，比前版新增 9 个场景；保留全部原有检查。

覆盖：两种 PNG 的尺寸、尖端锚点、选中层级、无图占位、实际来源合成、来源／状态缓存、照片与导出失败回退、中央云下载与临时文件清理、旧照片防覆盖、48 个地点增强预算、96 项任务上限、隐藏后迟到导出清理和 callout 点击。

Canvas 测试是模拟调用，**未执行微信原生 Canvas 的真实渲染与地图验收**。设计预览由相同构图和资源生成，不冒充真机截图。

## 如何使用最新包

- 重新导入／编译前端，确保 `images/markers/` 下四张 PNG 均在小程序包内。
- 本批没有云函数变更；已部署上一版配套 `mealRecords` 的环境无需为标记再部署云函数。
- 不需要清除本地数据、重新上传照片或修改数据库。

真机请核对：巴奴选中居中、所选绿勾、切换到另一门店、切回同一点、快速切换照片、无图记录、断网占位、深浅色及重新进入 Map。若只看到占位，应检查该照片的读取权限以及 Canvas 导出错误；不要通过公开存储桶解决。

## 后续可读性更新

用户反馈真机照片标记可以显示，但相邻点重叠。后续已增加数量聚合入口、200ms尺寸缓动、卡片收起及照片增高，见 MAP_READABILITY_UPDATE.md。此反馈不代表所有 Canvas／权限／离线项目已验收通过。
